## Deterministic assignment and temporal test

`configs/evaluation.json` fixes seed 366, namespaces, bucket cutoffs, five folds, minimum-size gates and decision rules. For each string PERSONID, compute SHA-256 of UTF-8 `namespace|366|PERSONID`, interpret the first eight digest bytes as an unsigned big-endian integer, and reduce modulo 10,000. The held-out namespace assigns buckets 0–2499 to held-out participants. Independently, a development namespace assigns remaining participants to tuning (0–6999), calibration (7000–8499) or threshold selection (8500–9999). A third namespace modulo five fixes each tuning participant's validation fold. Namespaces and exact ordering are in configuration. This is stable across row ordering, Python hash randomization and later appearance of other participants. No labels, outcome stratification, split search, seed retries or outcome-based reassignment are used.

Assignment covers all 11,717 baseline-eligible people from the internal ledger, including those without a labeled record. Of these, 2,929 are held out, 6,212 assigned tuning, 1,268 calibration and 1,308 threshold selection. Not all assigned people have usable development records.

The test contains only held-out people's eligible, valid-outcome Wave 7→8 records: **1,243 records from 1,243 people**. All their earlier labeled records (6,516) are excluded from every model-development purpose. For non-held-out people, only starting Waves 1–6 (follow-up Waves 2–7) can enter development. Their 3,663 Wave 7→8 records are excluded, not repurposed for tuning. A returning participant may contribute several earlier intervals within one development role and fold, never across roles. No requirement for all-eight-wave participation is introduced.

The prespecified minimum is 500 test records; the fixed split passes without an alternative protocol. This operational minimum is not a power calculation or guarantee of narrow uncertainty. No test positive count was consulted to accept or adjust the split. If an eventual metric is undefined because of class absence, report that fact; do not reseed or rebalance. If a size or development-case gate fails on another authorized dataset, stop and document a new protocol before modeling while preserving this lock. Never search final-test labels for a better partition.

Stage 4 already produced whole-cohort descriptive counts before assignment. Stage 5 reads only test keys to make the lock and inspect its size; it does not load test predictors or outcomes, publish test prevalence, or use them for any development choice. Test rows stay in the existing ignored cohort rather than being copied to a conveniently accessible modeling table. The final test is for later-wave, held-out participants within the observed local cohort, not necessarily people new to PATH, a nationally representative sample, or a causal study.

Five tuning validation folds have respectively 2,799 / 2,619 / 2,537 / 2,861 / 2,941 records, 946 / 910 / 900 / 984 / 952 people, and 292 / 302 / 299 / 296 / 298 positive records. Each exceeds the fixed minimum of 30 positives and 30 negatives. Calibration and threshold partitions each exceed 50 positives and 30 negatives. Counts are records, not independent events; people may have positive records in multiple intervals. Counts establish feasibility, not statistical independence or performance. Training in each fold uses the other four tuning folds only.

1. **Hyperparameters, feature choices and model selection:** use tuning participants only. Fit a fresh complete sklearn Pipeline in each fold, including imputation, encoding, scaling, feature selection and any train-only resampling. Do not fit these on a combined train/validation frame. Candidate features must come from the locked 25-feature baseline allowlist; identifiers, interval administration, outcomes, QC and reason metadata are excluded automatically by projection. Any learned feature subset must be chosen inside training folds. Select by the mean five-fold participant-weighted validation average precision. Fix candidate complexity order before fitting and choose the simpler candidate on an exact score tie. Report ROC-AUC as a secondary metric rather than changing the selection objective after seeing results. No test features may inform missingness-based selection or hyperparameters.
2. **Final base-model fit:** after model selection, refit an unfitted full Pipeline on all tuning records only. Preserve calibration/threshold people as separate holdouts. The selected model is frozen before probability calibration. No later refit incorporating calibration or threshold people is authorized by this protocol.
3. **Probability calibration:** score only calibration participants with the frozen base pipeline. Fit sigmoid calibration using their predictions and labels, with participant metric weights, without refitting base-model preprocessing or classifier. Do not compare many calibrators and pick one on threshold/test results. Retain the uncalibrated baseline for descriptive comparison and report any calibration limitations honestly. No calibrated probability or personal confidence claim is established in stage 5.
4. **Threshold:** score threshold participants using the frozen calibrated model. Select the threshold maximizing participant-weighted F1; ties choose the larger threshold. Report sensitivity, specificity, precision and confusion counts at that fixed threshold later. This is a course classification operating point, not a clinically validated intervention threshold. Do not invent low/medium/high risk categories or a personal confidence percentage; category validity requires a separate stated validation plan and adequate data.
5. **Final evaluation, later authorized stage only:** freeze model, calibration, features, threshold, plots/metric definitions and artifact fingerprints before opening test features/outcomes. Score the locked Wave 7→8 test once, without balancing, resampling or tuning. Report observed prevalence, average precision, ROC-AUC, Brier score, log loss, calibration curve, confusion counts and threshold metrics with uncertainty where defined. No test performance is reported now. Preserve a saved evaluation result rather than repeatedly opening the test for model comparisons.

Internal CV pools earlier waves, so it estimates generalization to held-out people in that period mix; it is not a rolling-origin forecast at every early interview. The outer test additionally restricts time and participant identity. Never silently label an ordinary overlapping-person time split as this strict held-out-participant test.

## Metrics, repeated rows and uncertainty

For development selection/validation, give each participant total weight one within the evaluated partition: each of their n interval rows receives weight 1/n. Compute average precision and other probabilistic metrics using those weights; also report unweighted interval metrics and interval-specific counts as secondary descriptions. Do not duplicate or suppress records to change the observed outcome distribution. Participant-equal metrics target an average across observed people; ordinary interval metrics target an average across observed eligible intervals. Report both meanings explicitly. Mean fold AP is the prespecified model-selection score; fold standard deviation is descriptive, not an independent-sample confidence interval.

Use a participant-cluster bootstrap for reported uncertainty: seed 366, 1,000 replicates, sample participants with replacement and bring all their evaluated interval rows together. Count each sampled cluster occurrence separately when computing participant weights (do not collapse duplicate draws). Use percentile 95% intervals; report effective valid replicate counts and undefined one-class replicates. This is conditional on the fitted model and observed follow-up sample, not an estimate of all model-development variability or survey-design uncertainty. The outer test has one interval per person, so its cluster bootstrap reduces to participant resampling. No bootstrap, metrics or model evaluation is run in stage 5.

## Class weighting, survey weighting and missing follow-up

Class weights address training-class imbalance and may change fitted decision scores and probability calibration. They may be configured or tuned only using tuning training folds. Resampling, if later justified, belongs inside training folds; evaluation partitions retain their naturally occurring rows and prevalence. Participant metric weights correct repeated-record contribution for a stated estimand; they are different from class weights.

PATH survey weights address sampling, nonresponse and the target population under a matching survey design. Class weighting or participant metric weighting cannot substitute for survey weights, strata or PSU handling. The local later waves lack matching design files, so this project remains unweighted with respect to the survey and makes no national inference. The outcome-observed cohort can be selected by informative attrition; missing follow-up is not a negative outcome and the ledger is not silently added to supervised training.

## Files, reproducibility and boundary checks

Run from the workspace root with the existing Python 3.13.5 interpreter; no dependency installation was needed. Versions are in `requirements-lock.txt` and the local split manifest (including pandas, pyarrow and scikit-learn).

```bash
.venv/bin/python scripts/create_evaluation_splits.py
.venv/bin/python scripts/verify_evaluation_splits.py
.venv/bin/python -m pytest -q -p no:cacheprovider
.venv/bin/python scripts/verify_inputs.py
```

Ignored local `artifacts/evaluation_v1/participants.parquet` contains each eligible participant's role and tuning-fold number (-1 outside tuning). `records.parquet` contains every labeled cohort key and its role/fold/partition; there are no predictor or outcome columns. `manifest.json` fingerprints the source cohort outputs, configuration, split implementation, dependency versions and membership/report files. Public `reports/evaluation_protocol_v1.json` contains only aggregate development counts, test size and checks; never participant IDs or individual rows.

`create_evaluation_splits.py` creates files exclusively and thereafter verifies and reuses the lock. It refuses changed/incomplete signatures or membership rather than regenerating. Preserve this lock on retries and any future correction; do not delete, rehash or change namespaces to bypass a failure. No Git operation or upload is needed. Code changes require an explicitly documented provenance migration or separate version while preserving the original membership, never an outcome-selected new assignment.

`src/path_project/evaluation.py` asserts stable hash assignment, unique keys, disjoint participant roles and folds, adjacent intervals and temporal restrictions. `select_keys` has no test/excluded accessor. `load_development` uses a predictor allowlist and Parquet participant/wave filters before returning labels/features. `fit_training_pipeline` rejects a batch unless its keys exactly match the authorized training partition; it clones a full sklearn Pipeline before fitting. The public `src/path_project/training_boundaries.py:fit_development_pipeline` loads its own locked tuning batch and verifies the mapping fingerprint and requested candidate subset, so callers cannot supply future columns or held-out rows. Future stages should use this public entry point. Calibration/threshold batches are score-only inputs to the frozen base model, not base-model fitting inputs; their later fitting/scoring implementation must keep the boundaries stated above.

`tests/fixtures/synthetic_evaluation.json` contains only invented participants. Tests reject held-out, future-period, calibration, threshold and validation rows in base fitting, forbidden features, changed assignments and duplicate batches. A synthetic Pipeline fit proves preprocessing sees only the authorized training fold and leaves the original estimator unfitted; no real PATH model is fitted. Tests also check deterministic ordering, participant-disjoint folds, lack of a test accessor, participant metric weights and the public fitter's self-loaded feature allowlist.

Stop after protocol verification. Model development and final evaluation require their own numbered stages.
